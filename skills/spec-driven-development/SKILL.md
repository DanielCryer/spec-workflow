# Spec-driven: спеки, планы и журналы решений

Режим для крупной работы: сначала фиксируем, что и почему делаем, по ходу — решения и проблемы, в конце — итог. Артефакты живут в отдельном репозитории спек и не смешиваются с кодом.

**Корень репозитория спек — переменная `SPECS_ROOT`.** Не задана — спроси путь один раз и держи его на сессию. Путь в тексты и конфиги не хардкодить.

**Структура каталогов — README репозитория спек** (шаблон для нового — `templates/specs-repo` в корне библиотеки, из base dir скилла это `../../templates/specs-repo`). **Правила ведения записей — `references/formats.md`** рядом с этим файлом. Расходятся — структура по README, правила записей по `formats.md`.

## Когда включать

Только по явной просьбе: «работаем по спекам», «spec-driven», «заведи спеку», «где спека по …». Режим держится до конца задачи или до явной отмены.

Можно **один раз предложить**, если задача совпала хотя бы по одному критерию:

- затрагивает 2+ кодовых репозитория;
- это проект с этапами или несколько эпиков, а не один тикет;
- работа рассчитана больше чем на неделю;
- есть архитектурные альтернативы, которые придётся обосновывать;
- результат нужен другим командам.

Предложить — не начать. Без согласия режим не включать и папку не заводить.

## Когда не включать

Правка на час, разовый багфикс, рутинный рефакторинг, задача с готовым решением. Спека в таких случаях стоит дороже, чем экономит. Если сомневаешься — спроси, а не заводи папку.

## Где что лежит

```none
<SPECS_ROOT>/
├── TASKS.md      # индекс: папка → ID → статус
├── README.md     # правила структуры: единица работы, этапы, форматы файлов
├── AGENTS.md     # те же правила языком агента
└── tasks/<папка>/
    ├── index.md       # обязателен всегда: статус, ID, ветки, PR, скоуп
    ├── decisions.md   # журнал решений, текущая редакция
    ├── problems.md    # журнал проблем, текущая редакция
    ├── notes.md       # черновики: мысль в работе, не история
    ├── todo.md        # действия вне этапов, не история
    ├── spec.md        # требования (когда их надо согласовывать)
    ├── plan.md        # карта этапов (когда порядок неочевиден)
    └── stages/NN-*.md # этапы проекта, если их несколько
```

## Перед работой: что прочитать

1. `TASKS.md` — если известен только ID задачи.
2. `tasks/<папка>/index.md` — вид работы (`project` / `problem` / `research`), статус, все ID, репозитории, ветки, PR, скоуп.
3. `decisions.md` — сводка `## Действующие решения` в начале, дальше заголовки. Полный текст — по номеру (`grep '^## D43'`). Это ответ на «почему так». Журнал целиком не читать: он растёт.
4. `problems.md` — до того, как чинить в затронутой области: возможно, уже наступали.
5. `spec.md` / `plan.md` / `stages/*` — по необходимости.
6. `notes.md` — черновики, если есть: не решение, не цитировать.
7. `todo.md` — действия вне этапов, если он есть: не решения, не история.
8. Шапка `decisions.md`: `**Последняя ревизия:**`. Прошло больше недели (при активной работе — 2–3 дня) или набежало >8 записей — предложи ревизию.

Нет файлов кроме `index.md` — это lite-режим, вся суть в карточке. Не считать это незаполненной спекой.

## По ходу работы: что писать

- Новое решение с альтернативами → запись `D<N>` в `decisions.md`.
- Наступил на проблему и обошёл → `P<N>` в `problems.md`.
- Закрыл этап или поменял статус → `index.md` и `TASKS.md` одним коммитом.
- Появились требования, которые надо согласовывать → `spec.md`. Этапов стало больше трёх → `plan.md`.
- Действие, которое не входит ни в один этап и не требует ID, → `todo.md`: чекбокс, строка, источник. Выполнил — удалил.
- Мысль ещё не решение → `notes.md`, без номеров.

**Перед любой записью в `decisions.md` прочитай `references/formats.md`**: там формат полей, бюджет строк, тест «если завтра запись исчезнет — кто-нибудь сделает иначе?», правила ревизии и запрет переписывать историю. Без этой сверки запись почти всегда уезжает в эссе.

## Связь с кодом

- Ветка: `<фактический TASK-ID>-<kebab-slug>`.
- Заголовок коммита: `[<фактический TASK-ID>] <English summary>`. Подзадача подписывается своим ID, а не ID проекта.
- В теле коммита или PR: `Spec: <SPECS_ROOT>/tasks/<папка>/`.
- Хеши значимых коммитов — в `index.md` или в записи журнала.

## Коммиты в репозитории спек

- Один коммит — одно изменение: новое решение, новая проблема, закрытый этап, смена статуса.
- Заголовок на английском, тело по-русски, по существу.
- Без `--amend`, rebase и squash: путь к решению — тоже артефакт.
- Не коммитить обрывки «чтобы не забыть» — для этого есть «Открытые вопросы» в `index.md`.

## Закрытие

- `index.md`: статус `done`, заполнен «Итог» — что сделали, чем закончилось, что осталось.
- Журналы отражают реальность: новые записи дописаны, статусы старых обновлены.
- `TASKS.md` обновлён.
- Если из спеки есть вывод, полезный команде, — он перенесён в вики. Каталог вики берётся из `WIKI_ROOT`, если переменная задана, иначе спроси, нужно ли переносить и куда.

## Антипаттерны

- Пересказывать описание задачи из трекера вместо ссылки на ID.
- Заводить пять файлов «по шаблону» на задачу без содержания.
- Писать спеку после релиза для отчётности — ценности нет, только вид работы.
- Складывать в спеку секреты, пароли, внутренние адреса с доступами.
- Разносить этапы одного проекта по отдельным папкам: теряется связь «прототип → кодогенерация → внедрение».
- Включать режим самовольно на любой крупной задаче.
- Писать запись-эссе на 30–50 строк: это либо несколько решений, либо не решение.
- Доливать в `Контекст` пересказ кода, который агент только что прочитал: через месяц он врёт.
- Сочинять альтернативы, которых не рассматривали, — фальшивый след мысли.
- Оформлять набросок сразу решением и потом «охранять» его от правок.

## Гейт

Детерминированная проверка формы — `scripts/spec_check.py` рядом с этим файлом. Запуск из base dir скилла:

```sh
python3 <base>/scripts/spec_check.py --spec <SPECS_ROOT>/tasks/<папка>
```

На Windows вместо `python3` подойдёт `py`. Скрипт берёт репозитории из `repos:` в `index.md` и ищет их под `PROJECTS_ROOT` (по умолчанию это родитель `SPECS_ROOT`, если он задан, иначе `~/projects`). Значение `repos:` — имя, путь к подмодулю или `имя=путь`. Где искать имена, задаёт `code_roots:` (пути от `PROJECTS_ROOT`, например `beta/Sources`), без него берутся `src`/`tests` репозитория или он целиком. Переопределения: `--repo NAME=PATH`, `--projects-root`, `--file-root`, `--strict`.

**Тесты гейт не запускает.** Прогон — работа исполнителя, результат живёт в карточке шага. Гейт проверяет только то, что отмеченный пункт `plan.md` вообще ссылается на коммит, файл или тест.

Код читается на C, C++, Python, TypeScript и QML (`_CODE_SUFFIXES` в скрипте): имя в бэктиках из отмеченного пункта должно встречаться в файле одного из этих языков. Проверяются `plan.md` и `stages/*.md`. Имена сравниваются как текст, а не разрешаются как символы: ренейм в другой ветке, имя в комментарии или в вендорном каталоге гейт не отличит. Вендорные и build-каталоги (`Externals`, `build`, `third_party`, `vendor`, `node_modules`) не читаются никогда.

Сводку решений гейт читает по смыслу: в блоке «Действующие решения» достаточно упоминания `D<n>` в любой форме — построчно или тематическим дайджестом. Надгробия (`влито в D<n>`) в сводке не нужны. `--index strict` требует ровно строку `- **D<n>**` на запись, `--index off` выключает проверку индекса.
