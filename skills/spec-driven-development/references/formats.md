# Форматы записей

Правила для файлов внутри `tasks/<папка>/`. Структуру каталогов задаёт README репозитория спек, здесь — как писать содержимое.

## index.md

Единственный обязательный файл. Front-matter — машиночитаемые поля, тело — карточка.

```yaml
---
task: FRONT-9102        # основной ID задачи в трекере
ids: [FRONT-9102]       # все ID папки, включая основной
kind: project           # project | problem | research
parent:                 # основной ID проекта, если папка выделена из него
title: Короткое название работы
status: in-progress     # draft | approved | in-progress | done | cancelled | shelved
mode: step              # quick | step | run — см. скилл controlled-work
created: 2026-11-03
updated: 2026-11-12
repos: [core, api]      # имя, путь или имя=путь (подмодуль: beta/Sources/UiFramework)
branches: {core: FRONT-1234-short-slug}   # репозиторий: ветка
pr:                     # ссылка на PR, если есть
tags: []
code_roots: [core/src]  # где искать имена и маркеры; по умолчанию src/tests или весь репозиторий
ref_roots: [../shared]  # дополнительные корни для ссылок на файлы вне репозиториев
aliases: [старое имя]   # прежние имена папки/задачи, для поиска
---
```

`status` — стадия работы: `draft` (пишу, ни с кем не согласовано), `approved` (подход согласован, можно делать), `in-progress` (работа идёт), `done` (закрыто, «Итог» заполнен), `cancelled` (отказались, причина в `decisions.md`), `shelved` (отложено, условие возврата записано в `index.md`). `mode` — ритм прогона, см. скилл `controlled-work`.

Гейт читает `repos`, `code_roots` и `ref_roots`, разделитель — запятая; относительные пути считаются от `PROJECTS_ROOT`. `repos` — имя (`core`), путь (`beta/Sources/UiFramework`, имя — последний сегмент) или псевдоним (`UiFramework=beta/Sources/UiFramework`). `code_roots` сужает поиск имён и `shortcut:`-маркеров. `ref_roots` добавляет корни для ссылок на файлы вне репозиториев.

В теле: «Скоуп» (что входит и что намеренно нет), «Открытые вопросы» (единственное место для них), «Итог» при закрытии, ссылки на ветки и PR. Решения по номерам здесь не перечислять — только сводные таблицы по теме.

## decisions.md

**Журнал — текущая редакция, не хроника.** Читатель должен понять правило сегодня, не восстанавливая историю.

Шапка файла:

```markdown
# Решения

**Последняя ревизия:** 2026-11-03
```

Журналов два уровня:

- `decisions.md` в корне задачи — сквозные решения: те, по которым работает кто-то вне этапа, и те, что переживают этап. Сводка `## Действующие решения` обязательна только здесь;
- `decisions.md` внутри папки этапа — решения этого этапа. Сводки в нём нет: что решено, видно по заголовкам, а `stage.md` ссылается на нужные номера.

Локальное решение в корень не пишется. Сквозное пишется в корень сразу, если от него зависит незакрытый чужой этап; иначе — при закрытии этапа, на ревизии. Критерий: «если бы запись исчезла, кто-то вне этапа сделал бы иначе?»

Решение, вынесенное в правило `rules/`, остаётся записью того этапа, где принято: правило — живой носитель, запись — его «почему». Поэтому в корне остаются действующие сквозные решения, ещё не ставшие правилами.

Заголовок сводки — ровно `## Действующие решения` (или `## Active decisions`): по нему гейт находит блок в режиме `--index summary`. Внутри блока номер считается проиндексированным, если он упомянут в любой форме — построчно `- **D7**` или тематическим дайджестом.

Ревизия — для каждого журнала отдельно, когда прошло больше недели (при активной работе 2–3 дня) или набежало больше 8 записей. Ревизия значит: перечитать, слить дубли, обновить статусы, а не переписать историю. Дату `**Последняя ревизия:**` держит корневой журнал.

Запись:

```markdown
## Dtc.3. [ID-подзадачи] Короткое имя решения

- **Контекст:** 1–2 строки, зачем вообще выбор. Без пересказа кода.
- **Решение:** что теперь считается правильным.
- **Альтернативы:** реально рассмотренные — с причиной отказа. Не было — `—`.
- **Последствия:** только «что теперь нельзя делать иначе». Без todo.
- **Статус:** действует
- **Ссылки:** repo@commit, файл, PR
- **Правило:** rules/masks.md      # только если решение стало правилом
- **Было:** D17                   # только если запись переехала из другого журнала
```

Метка этапа в заголовке не нужна: этап уже в номере. ID подзадачи в квадратных скобках ставят, когда запись отвечает на конкретный тикет.

Тело — до 12 строк, сведённая запись — до 18. `**Статус:**` — одно слово плюс от силы `(объединено с D4)` или `(заменено D9)`. Подробности — в тексте.

Перед записью три вопроса: это выбор? альтернативы реально обсуждались? это не пересказ `spec.md` или кода и не следствие уже записанного решения? Хотя бы один «нет» — писать не сюда: требование → `spec.md`, «решим позже» → «Открытые вопросы» в `index.md`, набросок → `notes.md`, состояние кода и порядок работ → `stage.md`, наступил и обошёл → журнал этапа.

Прежде чем заводить номер, сверься с журналом: `grep '^## D' decisions.md` и блок «Действующие решения». Уточнение, продолжение или замена уже записанного — не новая запись: правится родительская, в её заголовок дописывается `+ D<n>`, а номер новой записи, если он уже был заведён, остаётся надгробием `влито в D<n>`. Отдельный номер — только для темы, которой в журнале ещё нет.

Тест: «если завтра запись исчезнет — кто-нибудь сделает иначе?» Нет — не пишем.

Решили иначе — перепиши запись, прежнюю формулировку допиши в альтернативы: `— было (до 2026-10-01): …`. Устаревший факт (путь, имя, число) правь молча.

**Журнал не ведёт прогресс.** Запись формулирует правило и причину, а не состояние работ: «диспетчер откладывается до процессорной базы», а не «база сделана, диспетчер отложен». Что уже сделано, видно из этапа и `plan.md`; отметка о выполнении устаревает от каждого закрытого шага и заставляет переписывать запись после работы, которая решения не меняет.

Нельзя: удалять нумерованную запись, переиспользовать номер, вычищать реально рассмотренные альтернативы. Решение влилось в другое — надгробие: заголовок, `— влито в D9`, `**Статус:** объединено с D9`.

### Нумерация

- Корневой журнал — голые номера: `D7`, `P3`.
- Журнал этапа — код этапа и точка: `Dtc.3`, `Ptc.1`. Код задаётся в `stage.md` строкой `**Код:** tc`: 2–8 строчных латинских букв, уникален в папке задачи.
- Код пишется всегда, в том числе в заголовке записи в её собственном файле. Сокращённой формы «просто `D3`» у этапа нет.
- Полный токен уникален в папке задачи. Голый `D7` вне корня означает корневую запись — у этапа такого номера быть не может.
- Дыры в корне не заполняются: новый корневой номер продолжает наибольший когда-либо занятый, а не берёт свободный. Иначе номер, уехавший в этап, будет выдан второй раз.
- Гейт проверяет повтор токена, ссылку на необъявленный номер и дыры в счётчике каждого файла.

Сводка и существование номеров проверяются по корневому журналу: номер считается проиндексированным, если он упомянут в блоке «Действующие решения» в любой форме (строкой `- **D1**` или в тематической сводке). Надгробие (`влито в D9`) в сводке не нужно: запись живёт под номером цели. Записи этапов в корневой сводке не перечисляются.

### Переезд записи

Номер принадлежит файлу: переезд между журналами меняет номер, и обе стороны держат пару.

- В корне — раздел `## Перенесено` строкой `- D17 → Dproto.3 — stages/prototype/decisions.md`.
- На новом месте — поле `**Было:** D17` в записи.

Ссылки в `index.md`, `spec.md` и `rules/` переписываются на новый номер в том же изменении. Старый номер остаётся только в строке переноса и в поле `**Было:**`, поэтому поиск по нему находит дорогу. Гейт сверяет пары в обе стороны: строка переноса ведёт в существующую запись, а каждая запись с `**Было:**` имеет строку переноса.

Обратный переезд — так же: решение этапа, которое переживает этап, уезжает в корень с голым номером, а в журнале этапа остаётся строка переноса `- Dtc.2 → D7` — путь не пишется, потому что цель и так корень.

### Решение стало правилом

Решение, которое отвечает на «как делать», а не «как договорились здесь», переезжает в `rules/<тема>.md`: в записи остаётся `**Правило:** rules/masks.md`, в правиле — раздел `## Источники` с номерами. Номер записи при этом не меняется.

Правило правится в том же изменении, что и решение. Расхождение в любую сторону — решение называет правило, которого нет в «Источниках», или правило ссылается на номер, который его не назвал, — ошибка гейта.

## problems.md

Проблема всегда чья-то: она живёт в журнале этапа, где на неё наступили. Корневой `problems.md` заводится, только если проблема касается всей задачи — сборка, стенд, инструменты; для остальных он не нужен.

```markdown
## Ptc.1. Короткое имя проблемы

- **Симптом:** что видно.
- **Причина:** почему; неизвестна — так и писать.
- **Обход:** как обошли сейчас.
- **Остаток:** что осталось нерешённым.
- **Статус:** обойдено
- **Ссылки:** repo@commit, файл, issue
```

Нумерация и правила те же, что у решений: корень — `P3`, этап — `Ptc.1`. Проблема без «Остатка» — это не проблема, а заметка.

Закрытые проблемы, которые больше не нужны для текущей работы, переносятся в `archive/problems.md`; запись сохраняет свой номер, в том числе кодовый (`Ptc.1` остаётся `Ptc.1`). В шапке архива — дата переноса и диапазон номеров, в живом журнале — строка индекса с диапазоном, статусом и ссылкой. Номера не переиспользуются, поэтому `grep '^## Ptc.1'` идёт через индекс.

## notes.md

Черновик: не история, без номеров, правится и удаляется свободно. Здесь же живёт карточка текущего шага — отдельной секцией `## Карточка шага` в конце файла, чтобы её можно было вырезать целиком. Закрыли шаг — карточка **переносится в `archive/`**, а не стирается; остальные блоки файла остаются. Доросло до решения — заводится `D<n>`, блок из `notes.md` вычищается. После закрытия этапа `notes.md` не держат.

## archive/

Назначенная история: карточки закрытых шагов, пунктов, крупных проверок. Нужна человеку, который через месяц спрашивает «почему тут так».

- **По умолчанию не читается.** Открывается только по ссылке из этапа, журнала или `index.md`; «на всякий случай» туда не заходят и содержимое в отчётах не пересказывают.
- Файл на шаг: `<шаг>.md`, шапка с датой, ветками и диапазоном коммитов. Внутри — чек-лист в том виде, в каком закончился, решения, принятые без человека, и «не проверено». Полный лог прогона не пишется: он в git и в чате.
- После закрытия файл не переписывается — это история, а не живой документ.
- Архив не заменяет журналы: решения и проблемы попадают в `decisions.md`/`problems.md` к моменту закрытия шага.
- Пункты этапа остаются в этапе строкой со ссылкой на архивный файл, иначе этап распухает с каждым шагом.
- Закрытые проблемы журнала переносятся в `archive/problems.md`, в шапке — дата переноса, а в `problems.md` остаётся строка индекса: диапазон номеров, чем закрыто, ссылка. Номера не переиспользуются. Файл один на задачу; делим по годам только если записей станет слишком много.

## todo.md

Действия, которые не входят ни в один этап и не требуют ID. Чекбокс, строка, источник. Выполнил — удалил. Больше 15 пунктов — гейт предупреждает: это уже план, ему место в `plan.md`.

## analysis/ и sources/

Собранные данные живут отдельным файлом, а не в теле решения: замеры, дампы протокола, разбор кода, чек-лист. `sources/` — то же для внешних документов: снапшот на дату, не канон.

- Шапка файла: задача или ID, дата, `repo@hash` и `**Статус:**` — `черновик`, `действует`, `устарел`. Устаревший файл не удаляется: статус и ссылка на замену.
- Один файл — одна тема. Вывод, который стал решением или требованием, переезжает в `decisions.md`/`spec.md`; артефакт остаётся источником деталей, и решение не должно читаться только через него.
- Сырьё — pcap, логи, выгрузки БД — в репозиторий не кладётся: в файле остаётся сжатая таблица, окно, дата и чем снято. Если сырьё остаётся снаружи, пиши, где оно и у кого, а не путь на своём диске. Гигабайтный лог прикладывается, только если он мал и без него вывод не проверить.

Ссылка на артефакт — в «Ссылках» `index.md` или в `**Ссылки:**` записи.

## rules/

Правила работы и справки по механике — то, на что ссылаются план, спека и решения.

- Одна тема на файл.
- Правило — «когда …, то …, проверка …»: что делать и чем это проверяется.
- Маршрут — порядок шагов перевода или внедрения, когда он неочевиден: пункт, выход, проверка.
- Справка по механике — «как устроено» → «правила» → «Источники»: сжатая механика языка, формата или протокола, на которую опираются несколько правил. Канон остаётся в `sources/`, справка — производная и ссылается на него; при расхождении прав канон.
- Ссылки на исходники — `путь:строка`; их существование проверяет гейт.
- Раздел `## Источники` обязателен: номера решений, из которых выведено правило. Обратная сторона — поле `**Правило:**` в записи решения; гейт сверяет обе стороны.
- Даты правки не пишутся: свежесть видна в git (`git log -1 --date=short --format=%ad -- rules/<тема>.md`), а файл за день может меняться несколько раз.
- Правило правится в том же изменении, что и решение. Если правило описывает то, что решение поменяло, а файл не тронут, гейт этого не увидит — это работа ревизии, а не проверки формы.

## spec.md, plan.md, stages/

- `spec.md` — требования, которые надо согласовывать: что входит, что нет, критерии приёмки.
- `plan.md` — порядок этапов, зависимости и риски. Чекбоксов нет: что сделано, видно в `stage.md`, а статус — в `index.md`. Иначе один и тот же статус живёт в трёх файлах и его правят в трёх местах.
- `stages/<slug>/` — папка этапа. Один проект — одна папка, этапы внутри неё. Имя — slug без номера: порядок задают таблица в `index.md` и `plan.md`, а номер в имени мешает переставлять этапы. Slug не меняется после первой записи: на него ссылаются журнал, правила и план. В папке:
  - `stage.md` — карточка: эпик, статус, зависимости, цель, чек-лист работ, границы этапа, критерий готовности; обязательна;
  - `decisions.md` и `problems.md` — журналы этапа, появляются с первой записью;
  - `analysis/` — замеры и разбор кода этого этапа, если понадобятся.

### Что считается этапом

Этап выделяют не по объёму, а по смыслу:

- **результат** — что изменится снаружи, когда этап закроется: поведение, API, экран, тест;
- **свои решения** — если решения двух половин не ссылаются друг на друга, это два этапа;
- **самостоятельность** — этап закрывается, не дожидаясь соседнего; если два этапа проверяются только вместе, это один этап;
- **трекер** — эпик или тикет, статус которого синхронизируется.

Вид работы — «сервер», «UI», «тесты», «DICH», «клиент автотестов» — этапом не является: это пункты чек-листа. Повод разделить этап — два независимых результата, а не размер файла. Исследовательский этап (прототип, разведка) ограничен не объёмом, а требованием закрыться: он длится столько, сколько нужно для ответа «работает или нет», а работа внутри идёт карточками шагов.

## Общие правила

- Даты — ISO `YYYY-MM-DD`.
- Факт из кода привязывается к коммиту: `<репозиторий>@<коммит>` и рядом путь к файлу (`Sources/quote_engine.cpp`). Хеш неизменен, поэтому такая ссылка не стареет. Путь стареет при переименовании, и это повод поправить запись, а не переписать историю.
- Спека самодостаточна: всё, на что она опирается, лежит в папке или воспроизводимо. Ни путей на свой диск, ни гигабайтов сырья — как это делается, в разделе `analysis/`.
- `файл:строка` — подсказка, а не факт: номер уезжает от любой правки выше. Пиши, только если строка объясняет лучше, чем имя символа.
- Один факт — один файл: открытые вопросы только в `index.md`, требования только в `spec.md`, собранные данные только в `analysis/`.
- `shortcut:` — только **комментарием** (`#`, `//`, `/* */`), условие возврата — в том же абзаце. В строке или докстринге маркером не считается.
- Номер записи принадлежит файлу: корень — `D7`, этап — `Dtc.3`. При переезде номер меняется, пара «старое → новое» остаётся с обеих сторон.
- **Папки не переименовывать и не перемещать.** Уточнения — в `aliases`.
- **Историю не выдумывать.** Причина неизвестна — так и писать. Альтернатив не было — `—`, а не сочинённые варианты.
